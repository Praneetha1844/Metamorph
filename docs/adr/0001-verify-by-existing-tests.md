# ADR 0001: Verify refactors with the existing tests

Status: accepted

## Context

A language model can return code that looks cleaner but behaves differently. We need an acceptance rule that is automatic, explainable and does not rely on the model grading itself.

## Options considered

1. **Ask the model to confirm equivalence.** Cheap, but the model is the thing being checked.
2. **Formal equivalence checking.** Strong, but not practical for general Python.
3. **Differential or property-based testing generated by the model.** Broader coverage, but the generated tests share the model's blind spots and add a second unverified step.
4. **Run the user's existing tests against the candidate.** Simple, deterministic, and anchored to something the user already trusts.

## Decision

Accept a candidate only if the **original, unmodified tests** pass against it. Before asking the model anything, run the same tests on the original source (the baseline). If the baseline fails, times out, or collects no tests, stop with `baseline_failed`.

## Consequences

- The guarantee is exactly "the supplied tests still pass". Untested behaviour can change silently. The README, the report and the UI all state this.
- Weak or missing tests give weak or no verification, which is why an empty suite is treated as a failure.
- The tests run in the same interpreter process as the candidate. A run passes only on exit code 0 with at least one test reported as passed, which stops accidental false passes such as an early process exit. The engine does not defend against deliberately hostile code that fakes the pytest summary; that is out of scope for a tool whose user supplies the tests and reviews the diff.
- A model could special-case the tested inputs. Reviewing the diff remains the user's job.
- Static metrics (radon) are reported alongside, but they never decide acceptance.

## Revisit when

Adding mutation testing to estimate how strong the supplied tests are, or generating extra tests as an optional, clearly labelled second signal.
